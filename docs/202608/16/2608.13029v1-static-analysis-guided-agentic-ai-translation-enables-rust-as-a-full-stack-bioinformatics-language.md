## 摘要
生物信息学领域长期受困于遗留代码——这些代码虽被广泛使用，但可能已无维护者，或使用现今已不熟悉的语言（如Perl、Fortran）编写。这带来了维护成本（技术债务），而动态类型语言也对环境产生负面影响，且未能充分利用现代硬件。遗留代码还可能存在安全或可靠性问题，使其不适合在临床环境使用。我们在此表明，智能体AI结合静态分析，可用于将遗留代码翻译为现代语言Rust。我们提供了提示词和配套软件以支持系统性翻译，并在常见的NGS和成像软件上进行了评估。我们在我们的软件Bascet上展示了成果：体积减少约80倍，构建时间缩短约10倍，关键步骤性能提升超过3倍。同时移除了Unix依赖，使Bascet成为唯一能够在原生Windows上运行（无需容器）的单细胞流程。因此，大规模重构生物信息学软件现在可以在有限预算内实现，从而能够开发更复杂的工具。

## Abstract
The field of bioinformatics struggles with legacy code - old code that is commonly used but may no longer have a maintainer, or may be written in an now-unfamiliar language (e.g. Perl, Fortran). This incurs maintenance cost (technical debt), but dynamically typed languages also negatively impacts the environment and fail to make use of modern hardware. Legacy code may also have security or safety problems that make it unsuited for use in clinical settings. Here we show that agentic AI, combined with static analysis, can be used to translate legacy code to the modern language Rust. We provide prompts and supporting software to aid systematic translation, and evaluate it on common software for NGS and imaging. We showcase the result on our software Bascet: Size was reduced by ~80x, build time decreased by ~10x, and performance of key steps improved >3x. Unix dependencies were also removed, making Bascet the only single-cell pipeline able to run on native Windows, without a container. Large-scale refactoring of bioinformatics software is thus now possible at a limited budget, enabling more complex tools to be developed.

- **硬件与环境挑战**：
  - R、Python、Matlab 等动态语言能耗比编译型语言高 50 倍以上；
  - 硬件资源日益稀缺，要求代码更高效；
  - CPU 架构向更高效计算形态演进，需要大规模重写软件。
- **临床安全需求**：遗留代码存在安全或可靠性隐患，不适合临床使用。
- **整体含义**：本研究提出一种"静态分析 + 智能体 AI"的系统化翻译方法，将遗留代码翻译为现代语言 Rust，力争使 Rust 成为覆盖生物信息学"全栈"的唯一语言，从而系统性地解决生态碎片化、版本冲突、分发困难和临床落地等问题。

## 2. 方法论：核心思想与技术细节

### 2.1 总体思路
- 使用**智能体 AI（Claude 与 Codex）** 执行翻译，同时开发**静态分析工具**来引导和验证翻译过程。
- 核心翻译原则（确保可审计性）：
  - 每个原始函数对应翻译为一个 Rust 函数；
  - 不引入额外的辅助函数；
  - 每个函数的逻辑独立、保守地保留；
  - 保持原始代码的组织结构和目录结构；
  - 命名系统映射为 Rust 的 snake_case。

### 2.2 翻译流程（理想化步骤）
1. 静态分析与翻译脚手架搭建（为所有函数生成存根）；
2. 首次完整翻译；
3. 在合成数据上测试（与原代码输出对比）；
4. 在真实数据上测试（与原代码输出对比）；
5. 基准测试与速度优化；
6. 源代码清理；
7. 添加惯用 Rust API，决定可选特性。

### 2.3 静态分析工具（自研支持软件）
- **CCC（Code Complexity Comparator）**：比较原始代码与翻译代码的调用图、函数复杂度（含类型、符号、循环复杂度、逻辑表达式），帮助定位结构偏差。
- **tracehash**：通过代码插桩，对函数输入/输出进行哈希，快速发现纯函数偏差和调用次数差异（高层逻辑失效）。
- **gdbtv（GDB Translation Verifier）**：并行 GDB 会话中锁定步进比较原始与翻译代码（类双模拟/关系 Hoare 逻辑思想）。

### 2.4 C 代码的特殊处理
- C 代码直接翻译会产生非惯用 Rust（大量 libc 调用、裸指针、手动内存管理），需额外进行"习惯化"重构。
- 重构要点：消除 C 类型和 C 字符串、用 `Vec<u8>` 替代、用 `Option` 表示可空值、用命名枚举替代强转、积极重构但不引入辅助函数。

### 2.5 并行化策略
- 按 CCC 提取的调用图进行**自底向上并行翻译**；
- 并行子代理有助于扩大搜索范围，避免"只盯着热点函数"导致的级联错误。

## 3. 实验设计

### 3.1 翻译目标语料库
- **约 40 次翻译尝试，35 个软件包成功**完成翻译并达到可用状态，涵盖三类别：
  1. 微生物与 NGS 上游软件（如 BWAMEM2、SKESA、GECCO、minimap2、STAR、Kraken2、Prodigal、Prokka 等）；
  2. 图像分析与空间组学相关软件（Bioformats、OpenSlide、Cellpose、Deconwolf、VTK、ITK、Micro-Manager、YOLOv11 等）；
  3. 上游库依赖（压缩与格式支持：jpegxr、HDF5、Blosc2、LZ4、Zstd 等）。

### 3.2 Benchmark 设置
- 基准测试涵盖**速度、RSS（内存占用）、构建时间、软件体积**等指标；
- 单个基准测试重点用于**回归检验**（即检查翻译是否偏离原算法），整体趋势用于定性判断；
- 在 Intel Xeon Gold 6138 2.00GHz、192GB RAM 上进行，涵盖不同线程数和数据规模，并使用真实数据（如 1 亿条 reads 级）。

### 3.3 对比方法
- 本研究属于"翻译转换"类工作，没有对比其他翻译方法（如其他语言/其他翻译器），而是**与原版代码进行 1:1 对比**（速度、内存、输出一致性）。
- 部分内部对比：Claude 与 Codex 在翻译保守性、bug 修复能力上的差异。

## 6. 主要结论与发现

- **可行性**：结合静态分析与智能体 AI，在有限预算（约 11 周订阅）内实现了大规模遗留代码到 Rust 的系统性翻译。
- **Bascet 案例成果**：
  - 软件体积减小约 **80 倍**（容器 200MB → 裸二进制）；
  - 构建时间从 20 分钟降至约 **1-2 分钟**（约 10 倍提升）；
  - 关键步骤性能提升 **>3 倍**；
  - 移除 Unix/Posix 依赖，成为**首个可在原生 Windows 运行的单细胞流程**（无需容器/WSL2）。
- **生态改进**：
  - 用 Cargo 统一管理依赖，消除 Conda 和容器需求；
  - 跨编译支持 Apple M3 等新架构；
  - 上游软件作为 Rust 库直接调用，避免了 CLI 启动开销和 Unix 管道不兼容问题。
- **性能趋势**：
  - 大多数翻译后代码的速度与原版相当或更快；Java 翻译加速显著；Python/R 的提升高度依赖其底层 C/C++ 扩展占比；
  - 内存（RSS）表现不一，部分翻译因 Rust 所有权模型反而更高。
- **挑战**：
  - **浮点运算非交换性**导致 p 值微小偏差，需谨慎处理；
  - **元编程密集型代码**（如 BLAST 的 C++ 模板与代码生成）是当前方法的主要障碍；
  - C 代码翻译需额外惯用化重构才能获得 Rust 的内存安全保证。

## 7. 优点与亮点

- **首创性**：首次系统展示"静态分析 + 智能体 AI"组合用于生物信息学遗留代码的大规模 Rust 翻译。
- **可审计性设计**：坚持 1-1 函数映射核心原则，使翻译结果可逐函数审计、追踪上游更新（案例：openslide 和 minibwa 更新不到 1 小时完成）。
- **工具链创新**：自研 CCC、tracehash、gdbtv 三个静态分析验证工具，弥补了 LLM 在大型代码库上结构跟踪能力的不足。
- **实用价值高**：Bascet 案例展示了从"容器 + Conda + Linux-only"到"单一裸二进制 + 跨平台"的显著改进，对临床落地和资源受限场景极具意义。
- **版权与来源透明**：翻译均保留原 LICENSE、记录 git hash、引用原作者，回应了 AI 生成代码的版权关切。
- **成本可量化**：给出了订阅、token 消耗、时间周期等实际成本数据。

## 8. 不足与局限

- **实验方面的局限**：
  - 各软件的 benchmark 不统一，结果**只能定性解读**；
  - 翻译成功率约 87.5%（35/40），但失败案例（BLAST）的分析较为简略；
  - 翻译引入的 bug 率未被量化，且 AI 代理有"遗忘内存"的倾向（造成内存泄漏），仍需人工审计。
- **技术局限**：
  - **元编程/模板重代码翻译困难**，C++ 模板不能直接映射 Rust 泛型；
  - C 代码翻译产物初期非惯用且不安全，需额外重构；
  - 浮点运算顺序改变导致 p 值等结果微小偏差，影响严格复现；
  - 部分场景下 RSS 高于原版，进一步降低需要放弃 1-1 翻译或引入 unsafe。
- **偏差风险**：
  - 作者单方面使用 AI 生成基准测试提示，且承认 Codex 比 Claude 生成的基准更公平；
  - 作者同时是工具开发者和翻译执行者，存在潜在的利益相关偏差；
  - 大规模 AI 翻译若广泛采用，可能增加软件供应链攻击风险（类似 npm 生态问题）。
- **外部有效性与推广性**：
  - 提示词的效果依赖工作区中的隐式上下文，作者明确表示"对其他用户可能效果不佳，需要独立测试"；
  - 未与 Rust 替代方案（如手动重写、其他转译器）进行成本/质量对比。
