## 摘要
网络正越来越多地被 AI 代理而非人类访问。每个代理都需要知识，尤其是在生命科学领域，那里的代理化流水线正在快速发展。获取文献是这一需求的关键部分，诸如 Europe PMC 等资源（拥有超过 4000 万条索引记录）被广泛用于满足这一需求。然而，这些资源并非为 AI 代理而构建：它们接受关键词和复杂语法，并返回整篇论文，因此每个代理都必须学习语法、进行多次搜索，并阅读全文以找到所需的证据。我们提出 EMBL AI 图书馆员，这是一个知识层，为 AI 代理升级了 Europe PMC 接口：代理用自然语言提问，并获得回答问题的证据。一个单一的 LLM 编排整个知识检索过程：它规划由实时 Europe PMC 搜索引擎执行的互补子查询，然后阅读选定的论文并定位相关证据。我们在四个基准上评估 Librarian：文献综合、声明验证、开放域问答，以及下游生物学任务，如协议问题和序列操作。在 ScholarQABench 上，Librarian 的 Citation F1 比最近发表的强基线高出 16 个百分点以上。用作现有声明验证管道的检索层时，它提高了与专家共识的一致性；在开放式 LitQA2 基准上，GPT-5.4 代理在使用 Librarian 作为基础时比使用网络搜索得分高约 8 分。总的来说，我们的结果表明，为生命科学代理配备 Librarian 知识层可以提高一系列任务的性能。我们在 https://github.com/petroni-lab/librarian 公开发布我们的代码。

## Abstract
The web is increasingly accessed by AI agents rather than humans. Every agent needs knowledge, especially in the life-sciences, where agentic pipelines are growing fast. Access to the literature is a crucial part of that need, and resources such as Europe PMC, with over 40M indexed records, are widely used to meet it. Yet these resources were not built for AI agents: they take keywords and complex syntax and return whole papers, so every agent must learn the syntax, issue several searches, and read full papers to find the evidence it needs. We introduce EMBL AI Librarian, a knowledge layer that upgrades the Europe PMC interface for AI agents: an agent asks in natural language and receives evidence that answers it. A single LLM orchestrates the whole knowledge retrieval process: it plans complementary subqueries executed by the live Europe PMC search engine, then reads the selected papers and locates the relevant evidence. We evaluate Librarian across four benchmarks: literature synthesis, claim verification, open-domain question answering, and downstream biology tasks such as protocol questions and sequence manipulation. On ScholarQABench, Librarian improves Citation F1 by more than $16$ points over strong recently published baselines. Used as the retrieval layer of an existing claim-verification pipeline, it increases agreement with expert consensus; and on the open-form LitQA2 benchmark, a GPT-5.4 agent scores about $8$ points higher when grounded in Librarian than with web search. Overall, our results show that equipping life-science agents with the Librarian knowledge layer improves performance across a range of tasks. We release our code publicly at https://github.com/petroni-lab/librarian

### 一、核心问题与整体含义（研究动机与背景）

- **背景与动机**：随着 AI 代理（AI Agents）在网络流量中的占比持续上升，生命科学领域的代理化流水线也快速增长。这些代理深度依赖科学文献来支撑其推理、总结、假设生成和实验规划，但现有主流文献检索资源（如 Europe PMC，索引了超过 4,000 万篇文献）在设计之初是面向人类用户的：
  - **输入端**：要求用户（或代理）使用关键词和复杂查询语法，而非自然语言；
  - **输出端**：返回的是整篇论文（按相关性排序），而非精炼的证据片段，代理需要自行阅读全文、解析内容，消耗大量上下文窗口和算力；
  - **多别名问题**：生物学实体（基因、蛋白质、疾病等）存在多种别名，单一关键词查询往往查询不全，代理需要多次搜索才能覆盖。
- **核心问题**：如何为生命科学 AI 代理构建一个**知识层（Knowledge Layer）**，使其能够用自然语言提问，并直接获得紧凑、可引用、来源可追溯的证据片段，而无需自建索引、学习查询语法或阅读整篇论文。
- **整体含义**：论文提出了一种 "agent-first" 的文献访问范式——将文献检索从代理的负担中解耦出来，成为一个共享的、即插即用的基础设施层，使任何代理（无论其底层模型强弱）都能受益于专业化的文献证据支撑。

### 二、方法论：EMBL AI Librarian 的设计与核心思想

- **核心理念**：不做自己的向量索引，而是直接复用 Europe PMC 的实时、字段化检索基础设施，用**一个单一的 LLM 控制器**编排整个检索流水线。系统接受自然语言问题，返回经过筛选、排序的可引用证据片段列表。
- **三层流水线架构**：
  1. **Stage 1：子查询生成（Subquery Generation）**
     - 一个 LLM（Planner）将用户自然语言问题转换为至多 N=7 个互补的 Europe PMC 子查询，支持字段化语法（如标题、摘要、基因/蛋白质、生物体、疾病、化学物质、MeSH 词、发表年份等）。
     - 每个子查询在执行前会经过**确定性语法验证器**，不合格的查询被丢弃；若规划器输出不可解析，则回退为原始用户查询。
  2. **Stage 2：论文级检索与段落排序（Paper-level Retrieval & Paragraph Ranking）**
     - 验证过的子查询并行提交至 Europe PMC 搜索引擎，每个查询返回至多 P=50 条记录，构成至多 M=N×P 篇论文的候选池（去重按 PMID → DOI → title 分层进行）。
     - 每篇全文论文被解析为带小节标题和类型标注的段落；用 BM25 对段落按与原问题相关度排序；每篇论文最多保留 k=16 个段落进入下一阶段，摘要始终保留。
  3. **Stage 3：过滤、重排序与证据提取（Filtering, Re-ranking & Evidence Extraction）**
     - 段落被切分为句子并赋予唯一 ID，一次 LLM 调用（全文本批大小为 3）对句子进行交叉编码式联合评估，同时完成三件事：过滤无关句、对相关句排序、提取支撑证据。
     - 最终输出为按来源论文聚类的、有序的可引用证据片段集合，附带论文元数据和用于检索的 Europe PMC 查询——检索过程透明可审计。
- **关键设计细节**：
  - 系统**模型无关**：任何 LLM 都可作为规划器和过滤器的引擎，未来模型升级可自动继承收益。
  - 返回证据以句子 ID 而非重新生成文本的方式输出，大幅降低解码 token 数，节约延迟与成本。
  - 整条流水线从"recall-oriented"的检索逐步过渡到"precision-oriented"的证据筛选。

### 三、实验设计

- **数据与基准**：论文在四个互补的基准套件上评估 Librarian 作为知识层的效果：
  1. **ScholarQABench**（文献综合）：使用 Bio（1,451 题）和 Neu（1,308 题）两个多文档综合分块，以及 29 个多学科（Multi）子集（生物医学相关）。指标为 Citation F1 和 LLM 评分（1–5）。
  2. **ProClaim-eval**（声明验证）：包含 419 条来自 SIGNOR（蛋白-蛋白相互作用）和 ConnectomeDB（配体-受体相互作用）的声明，需给出 SUPPORT / REFUTE / UNCERTAIN 三种裁决，指标为与专家共识的一致率（Agreement）。
  3. **LitQA2**（开放域问答）：从原始 199 题中选取 91 题（支撑论文在 Europe PMC 有可获取全文的子集），转换为开放形式（非选择题），评价指标为覆盖率（Cov）、准确率（Prec）和精确率（Acc）。
  4. **LAB-Bench**（基础生物学能力）：选取 DbQA（数据库查询）、ProtocolQA（协议排错）、SeqQA（序列操作）、Cloning Scenarios（分子克隆）4 个子任务，排除图形（FigQA）、表格（TableQA）等 Librarian 尚不支持的模态。Librarian 结果使用公众子集（约占 80%），基线与人类专家引用完整 LAB-Bench 数值。
- **对比方法**：
  - ScholarQABench：OpenScholar（8B/70B）、PaperQA2、SciRAG（Llama-3.1-70B / GPT-4o），以及 BM25 + GLM-5 综合代理（同模型下对照检索器）；
  - ProClaim-eval：OpenScholar（基于 Semantic Scholar）、Verifier Agent + PubMed/S2 检索、原版 ProClaim（PubMed+S2）、Verifier Agent + Librarian、ProClaim + Librarian；
  - LitQA2：OpenScholar-8B、无检索（参数化记忆）、Web 搜索、Librarian（均为 GPT-5.4 骨干）；
  - LAB-Bench：GPT-4o 与 GPT-5.4 两种骨干，在 Base（无外部证据）和 +Librarian 两种条件下，外加 Claude 3.5 Sonnet 和人类专家参照。
- **裁判模型**：Citation F1 用 AttrScore AutoAIS 评估引用归因；LitQA2 用 GPT-4o 作为评判模型判断开放性答案是否正确；ScholarQABench 的 LLM 评分用 Prometheus。

### 五、实验数量与充分性

- **实验数量**：整体实验规模较充分——4 个基准套件、超过 3,000 道评测问题（ScholarQABench 1451+1308+29，LitQA2 91，LAB-Bench 1,261 题，ProClaim 419 条声明），覆盖多个任务类型。
- **消融与对照**：LitQA2 上同一骨干（GPT-5.4）在三种检索条件下（无检索/Web/Librarian）对比，隔离了检索器贡献；ScholarQABench 使用相同 GLM-5 综合代理对比 BM25 与 Librarian；LAB-Bench 用两种骨干分别做 Base vs +Librarian 对照。这些设计较好地将知识层的贡献从骨干模型能力中分离出来。
- **客观性与公平性**：
  - 所有 Librarian 的检索配置在所有基准中保持一致（N=7、P=50、k=16），避免了对特定任务的过拟合；
  - 但需注意：ScholarQABench 的 OSDS BM25 基线不包含子查询规划和过滤步骤，因此 BM25 vs Librarian 的差距混杂了检索策略与语料差异；LAB-Bench 的 Librarian 行使用了部分"参数化回退"（检索无果时按无检索基线回答），使对比并非纯粹的检索贡献；LitQA2 使用子集（91/199），排除了 Europe PMC 无全文的题目，不能等同于完整基准上的性能。
  - 缺乏对 Librarian 各组件（如子查询数量、BM25 段落数、过滤 LLM 的影响）的独立消融研究，属于实验覆盖上的一个缺口。

### 六、主要结论与发现

- **Librarian 作为知识层在四类任务上普遍带来一致提升**：
  - ScholarQABench：综合代理（GLM-5）装备 Librarian 后在 Bio 上 Citation F1 达 73.8（较 OpenScholar-70B 提 17.9 点，较 BM25+同模型提 6.8 点），Neu 达 79.4（+10.9 vs BM25），Multi LLM 评分 4.90（较同类基线提 20%）。
  - ProClaim-eval：将 ProClaim 的检索器替换为 Librarian 后，平均一致率从 0.75 提升至 **0.80**；即使单提示的 Verifier Agent + Librarian 也达到 0.66，远超 PubMed/S2 检索（0.51），说明 Librarian 本身承担了大量证据筛选工作。
  - LitQA2：GPT-5.4 + Librarian 的准确率达 **78.9%**，比 Web 搜索（70.3%）高 8.6 点，精确率 82.6 vs 76.2，覆盖率 95.6 vs 92.3；无检索时仅 17.6% 准确率。
  - LAB-Bench：GPT-5.4 + Librarian 宏平均准确率提升 **+4.2 点**（50.5 → 54.6），其中 SeqQA 提升最显著（52.5 → 63.8，覆盖率 85.0 → 98.8）；GPT-4o 则主要通过"精度换覆盖"实现校准（宏精度 +5.0，覆盖率 -5.4，准确率持平）。
- **知识层的价值随任务类型而分化**：文献密集任务（综合、验证、序列操作、克隆）收益明显；数据库查找式任务（DbQA）几乎无增益（准确率 -2.3 / -1.3），原因在于这类问题不需要文献证据，检索反而增加噪音。
- **核心启示**：即使是最强的前沿模型（GPT-5.4），在领域专业化知识层面前仍有提升空间；文献访问能力与模型本身解耦比"塞进更大的模型"更具可持续性。

### 七、优点与亮点

1. **无索引、低成本、即插即用**：直接复用 Europe PMC 的实时检索服务，省去构建和维护数百 GB 向量嵌入索引的基础设施开销，部署门槛极低。
2. **透明与可审计**：返回的每个证据片都附带来源元数据和生成它的 Europe PMC 查询，代理和用户都能追溯证据的出处，比向量检索的黑盒邻居查找更可信。
3. **模型无关性与可持续性**：检索控制器可由任意 LLM 充当，随着更强大模型的涌现，该系统无需重新设计即可自动受益。
4. **字段化检索的优势**：保留 Europe PMC 的富结构化字段（基因、蛋白质、生物体、化学物质等），使查询能够精确利用生物医学受控词表，比稠密向量的扁平语义相似度更灵活。
5. **设计上的务实考量**：包括语法验证和保守回退策略、层次化去重、XML 清理规则、输出 token 压缩（句子 ID 而非重生成文本）、检索配置全基准统一等细节，体现了工程严谨性。
6. **代码开源，可复现**：发布完整代码、提示词模板、运行时配置和评估流水线，有助于社区在其基础上集成与扩展。
7. **测评维度丰富**：覆盖开放综合到闭式事实检索的完整任务谱系，较全面地刻画了知识层的能力边界。

### 八、不足与局限

1. **知识覆盖受限于 Europe PMC 的收录范围**：部分付费（paywalled）论文的全文不可用，摘要仅能进入证据池，某些关键证据可能遗漏。作者计划扩展 OpenTargets、UniProt、ChEMBL 等 EMBL 生态的其他资源作为补充。
2. **不支持多跳检索**：当前 Librarian 只做单轮检索（尽管用多子查询提升召回），复杂的多跳问题需由下游代理自行解决。作者计划赋予 Librarian 在证据不充分时继续多轮搜索的能力。
3. **模态覆盖不全**：不处理图表（FigQA）、补充材料（SuppQA）等非文本内容，表格仅以文本形式处理，大量潜在的证据形态（如实验图像、补充数据表）无法被利用，意味着在相应任务上性能天花板受限。
4. **检索深度受限**：每篇论文只保留有限数量的段落（k=16）进入精排，某些分布在长文中的稀疏证据可能被截断。
5. **实验验证方面的偏置风险**：LitQA2 评测仅基于 91 题子集（Europe PMC 可全文获取的题目），不能代表完整基准的表现；LAB-Bench 的 Librarian 结果使用公众子集（约 80%）而基线使用完整集，对比口径不完全一致；ScholarQABench 的 BM25 对照缺乏规划与过滤环节，混淆了检索策略与语料来源的效应。
6. **缺少系统性的组件消融**：论文未单独验证子查询数量、BM25 候选数、段落预算、过滤模型的能力（弱模型 vs 强模型）等因素对最终性能的影响，组件级归因不够充分。
7. **下游任务的融合方式简单**：在 LAB-Bench 中，证据以 1,500 字符预算截断后直接注入单轮 prompt，没有针对每条证据的可信度做进一步权衡；当检索内容不相关时，代理被提示忽略，这可能导致部分题目实际上等价于无检索基线。
8. **性能与成本权衡未充分量化**：虽然论文声称句子 ID 解码降低了延迟和成本，但没有给出具体的延迟、token 消耗或 API 费用的量化数据，难以评估工程实用中的性价比。
